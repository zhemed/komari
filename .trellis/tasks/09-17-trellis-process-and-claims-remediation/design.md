# 设计：流程违规与结论可信性整改

## 1. 错误的分类（先定性，再整改）

| # | 错误 | 类别（break-loop 框架） | 性质 |
|---|---|---|---|
| E1 | 本轮从未调用 Trellis（无任务/PRD/检查/归档） | **Process Flaw**（流程缺失，非代码缺陷） | 严重：整个过程缺少强制门禁，直接导致 E2 无人拦截 |
| E2 | 未验证的因果结论进入公开文档（0.0.6 发布说明、MAINTAINING、代码注释、归档 PRD） | **E. Implicit Assumption** + **D. Test Coverage Gap**（无"判别性实验"这一步） | 严重：对外发布的说明是错的，用户会据此形成错误认知 |
| E3 | 被指出后仍以"小改动走直接改路线"淡化 | 归因/沟通错误 | 严重：妨碍整改 |

**E1 是根因，E2 是它的症状**：如果有 PRD，"待验证假设"与"已确认结论"就不会混在同一栏；
如果有 `trellis-check`，"写进发布说明的因果链有没有对应的判别性验证"就是必答项；
如果有 finish，归档记录里不会有错误结论而无人回看。

## 2. 更正策略（不重写历史）

- 归档任务、journal、已发布 release notes 都是**记录**：只**追加**带日期的更正块，不覆盖原文。
- 用户可见文档（`docs/MAINTAINING.md`）：直接把错误措辞改成**带证据边界的表述**——
  因为它是"当前事实"文档，不是历史档案；但要在同一条里说明"0.0.6 曾写成确因，在此更正"。
- 代码注释：直接改（注释描述的是当前代码的意图），并在注释里写明"没有证据表明曾在实测触发"。
- 公开 release notes：`gh release edit 0.0.6 --notes-file <累积版>`，追加"## 更正（2026-09-17）"段。

## 3. 预防机制设计（要能拦住下一次）

| 机制 | 落点 | 拦截的错误类型 |
|---|---|---|
| M1 证据标准指南 | `.trellis/spec/guides/evidence-and-claims-guide.md` | E2：写明观测 vs 推断、禁用措辞、判别性实验、全落点更正清单 |
| M2 发布说明措辞门禁 | `docs/MAINTAINING.md` §3.4 第 1 步 | E2：发布说明每条"修复/原因/已知问题"必须给出可执行验证 |
| M3 任务制强制 | 本任务 + Task A 的实际存在；`.trellis/spec/backend/index.md` 的 Pre-Development Checklist 指向指南 | E1：复杂改动必须先建任务 |
| M4 机械复查命令 | 指南与 PRD 里的 grep 命令（R4） | E2：更正后能一条命令确认没有残留 |

## 4. 取舍

- **不**引入"文档禁止写因果"这种极端规则：工程需要推断，规则只要求**标注证据等级**。
- **不**自动扫描"确因"之类词进入 `check-repo.sh`：白名单/上下文判断容易造成误报疲劳，
  改为把 grep 命令写进指南与本 PRD 的验收项（人工复核一次即可）。
- **不**重写 0.0.6/0.0.7 的 tag 或 release 内容（除追加更正段），发布物保持不可变语义。

## 5. 与 Task A 的边界

- Task A 承载 0.0.7 的**代码/发布**事实（已发生，补登）。
- 本任务承载**流程与文档可信性**整改；两者都完成才认为"本轮收口"。
