# 扫描残留任务 + 验证闸门修复

## Goal

盘点仓库里**残留的 Trellis 任务**（未完成、未归档、悬空引用、孤立目录、无主/僵尸任务），
给出每条的处置建议；同时验证修好的 Trellis 闸门是否恢复正常。

**本轮只读**：只盘点与建议，不删除、不归档、不改代码——清理动作等用户点头。

## 背景

- 上一轮（`10-23-traffic-month-rotate`）排查按月重置流量时，闸门 hook 误拦所有工具调用
  （只有含 `task.py create` 的命令能过），已向用户报告并给出定位提示。
- 用户反馈：闸门已修好，要求本轮顺便验证。
- 上一轮的排查任务本身仍处于 `in_progress` 且未归档 —— 属于本次要盘点的对象之一。

## 盘点范围（只读）

1. **活动任务**：`.trellis/tasks/*/task.json` 中 `status != completed` 的目录，
   含创建时间、最后修改时间、是否有 `prd.md`、是否被会话指针引用。
2. **会话指针**：`.trellis/.runtime/sessions/*.json` 里 `current_task` 指向的路径是否存在；
   指向已归档/已删除任务即为悬空。
3. **归档区**：`.trellis/tasks/archive/**` 是否有重复 slug、同名任务多次归档、缺 `prd.md` 的条目。
4. **孤立/半成品**：任务目录缺 `task.json`、缺 `prd.md`，或只有 `research/` 的空壳。
5. **仓库状态**：是否有未提交的任务目录（`git status`），避免"扫完就丢"。
6. **团队任务板**：`team_task_*` 里是否有属于本项目的历史残留（若有则一并列出）。

## 闸门验证（要给出实测输出）

- [ ] 普通命令（不含引导前缀）能通过；
- [ ] `grep` / `glob` / `read` 等非 bash 工具能调用；
- [ ] 任务处于 `in_progress` 时正常放行；**且**能说明"它仍在拦无任务的情况"（若可安全验证）。
- [ ] 记录验证时的命令与原始输出，作为"闸门已恢复"的证据。

## Acceptance Criteria

- [x] 每条残留任务给出：路径、状态、最后修改时间、判定依据、**建议处置**（继续/归档/删除/保留待定）；
- [x] 悬空指针（有指向、无实体）单独成表：实测 0 条；
- [x] 闸门验证给出实测命令与输出（放行侧通过；拦截侧未验证，见下）；
- [x] 全程只读：扫描期间零写入（侦察员以 md5/git status/新于时间戳三重自证）。

## Constraints

- 不得出现真实域名/IP/端口/主机名；
- 不清理任何东西（清理是后续独立任务）；
- 报告用五节：结论 → 改动清单 → 验证 → 风险与未完成 → 建议下一步，每条标注证据等级（实测/推断/待查）。

## 扫描结果摘要（2026-10-23）

- 活动任务残留 2 个（均 `in_progress`）：`10-23-traffic-month-rotate`（**无主**，无会话指针）、
  本任务本身；两者当时**均未提交**。
- 归档区 65 条**零坏账**：无重复 slug、无缺 PRD、无空文件、命名 65/65 一致、`status` 全 `completed`。
- 会话指针悬空 **0**；孤立/半成品目录 **0**；隐藏临时文件 **0**。
- `.trellis/.current-task` 不存在属正常（0.6.17 无写入点）；`.runtime/update-check-*.marker` 3 个为失效缓存。
- 机制事实：`task.py current` 在**子会话**按设计返回 `none`（按会话身份定位，不猜归属）——
  除 root 会话外看不到活动任务。
