# 设计：流量查询聚合语义

## 1. 问题模型

`traffic.up/down` 是 **gauge 类型但语义为"量"** 的指标：一个采样点 = 相邻两次上报之间新增的字节数。
存储层把每个采样点原样落库，桶聚合（`sum`/`avg`/`max`…）由查询决定，于是"选错聚合"在存储层无感。

| 聚合 | 数学含义 | 是否等于"该桶真实流量" |
|---|---|---|
| `sum` | Σ 各次上报增量 | ✅ 相等（实测逐分钟零误差） |
| `avg` | Σ ÷ 采样条数 | ❌ 恒小于真实值（每分钟 20 条 → 1/20） |
| `max` | 单次上报最大增量 | ❌ 只是峰值 |

## 2. 契约与优先级

```
按指标显式指定（aggregation_by_metric / algorithm_by_metric）
  > 指标语义默认（metricstore.SemanticAggregation）
  > 全局指定（aggregation / algorithm）
  > avg
```

理由：全局那项是**图表偏好**（面板默认 `avg`），不是针对某个指标的意图；
语义默认必须压过它，否则客户端默认值一改就把指标算错。要覆盖语义默认必须**指名道姓**。

## 3. 为什么修服务端而不是前端

- 前端已内嵌进服务器二进制（改前端=必须重新发前端产物），成本高；
- 任何第三方调用方（脚本、未来的 CLI）都会踩同一个坑，规则放在服务端只写一次；
- `metricstore` 与 records 路径本来就存在同一套语义约定，合并即可消除不一致。

## 4. 边界与兼容

- 不改变任何存储写入语义，只改读取时的聚合选择 → 无迁移、无数据变更。
- `net.total.up/down` 是 counter，`last` 为桶末值；面板"总流量"卡片读的是
  `client_traffic_totals` 累计表（0.0.6 引入），与本修复相互独立。
- 未解决（已记录）：不同分辨率（60s/300s）下 `sum` 的点值量级天然不同（5 倍），
  属于"每桶字节数"的固有含义。

## 5. 验证设计（判别性实验）

1. **记录侧是否有丢失**：同一分辨率下端点对齐逐分钟对拍
   （本桶 Σ增量 vs 相邻桶 `last_val` 差值）——必须自己证明测量方法自洽，禁止混用 60s/300s。
2. **查询侧是否正确**：复制 `data/`、备用端口起修复版实例，用**面板同款参数**对拍
   "返回点值 vs 库中真实量"，一个命令区分"数据丢失"与"聚合错误"两个假设。
