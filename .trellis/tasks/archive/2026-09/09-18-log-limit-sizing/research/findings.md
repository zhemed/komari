# 日志上限取值建议（实测数据，2026-09-18）

用 `ghcr.io/zhemed/komari:0.0.17` 起临时容器（host 网络、备用端口 25791、独立数据目录）实测，
测完已 `docker rm -f` + 删临时目录，无残留。

## 一、先摸清"日志从哪来"

| 事实 | 证据 |
|---|---|
| 面板的"日志"页读的是**数据库**，不是 docker 日志 | `web/rpc/jsonrpc/admin.system.go:69` 查 `models.Log`；docker 日志轮转**不会**影响面板里能看到的内容 |
| 数据库那份有 **30 天**保留策略 | `database/auditlog/log.go:30` `Delete logs older than 30 days` |
| stdout 只有两类：GIN 请求行 + 少量事件行 | 实测单行样例：`[INFO/GIN] 307 GET / \| 127.0.0.1 \| 10.7µs` |
| **空载完全不写日志** | 空载 120 秒增量 **0 字节 / 0 行** |
| **仪表盘常开也不写日志** | 浏览器登录后仪表盘挂 180 秒：**0 字节 / 0 行**（面板是推送驱动，不轮询） |
| 日志量 = 请求数 × 每请求 ~74 B | 300 次请求 → 22,152 B / 300 行（**74 B/行**） |
| 一次页面浏览 ≈ 4.6 KB / 44 行 | 浏览器依次访问 5 个页面 → 23,189 B / 224 行 |
| agent 默认 3 秒上报一次；v2 走 **WebSocket** | `agent/cmd/root.go:173` `--interval` 默认 3.0；`agent/server/websocket.go:43` |
| v2（WS）上报**不产生** HTTP 日志行；v1（POST）每报一行 | GIN 中间件只在 HTTP 请求时打行；WS 消息不落 GIN 日志 |

> json-file 每行额外封装约 **90 B**（`{"log":"…","stream":"stdout","time":"…"}`，
> 含 ANSI 转义）。这一项是**按格式推算**，不是直接读文件测的（读 `/var/lib/docker` 属工作区外）。

## 二、各场景落盘速率（按上面实测值重建）

| 场景 | 行/天 | 落盘/天 |
|---|---|---|
| 空载 / 仪表盘常开 | 0 | **0** |
| 面板浏览 100 页/天 | 4,400 | **0.8 MB** |
| 1 个 v1（POST）节点，3s 一次上报 | 28,800 | **4.5 MB** |
| 10 个 v1（POST）节点 | 288,000 | **45 MB** |
| v2（WS）节点（本仓库 agent 的默认形态） | ≈0（仅重连时几行） | ≈0 |

## 三、建议取值

```yaml
logging:
  driver: json-file
  options:
    max-size: "10m"     # 单文件 10 MB
    max-file: "3"       # 最多 3 个 → 上限 30 MB
```

- **典型部署**（v2 agent + 少量面板浏览）：30 MB ≈ **数周~数月**的历史，足够排查崩溃与升级问题；
- **跑老 agent（v1 POST）**：每个节点 ~4.5 MB/天 → 30 MB 约 **6 天**（10 个节点约 16 小时）。
  这种部署建议升到 `max-size: "20m"` + `max-file: "5"`（上限 **100 MB**），10 个节点约 2 天；
- 不建议低于 `5m × 2`（10 MB）：一次崩溃后的启动日志可能被冲掉，事后没法看；
- 不必更大：docker 日志只是"容器 stdout 的历史"，**面板日志页另有 30 天 DB 保留**，两者不冲突。

## 四、附带结论（与上一轮 compose 审查衔接）

- 版本号由你定，但**钉的版本要 ≥0.0.13** 才有一键升级能力（0.0.11 才有 helper 子命令）；
  日志上限与版本无关，`0.0.7` 那种只是占位值不影响本节结论。
- `docker logs` / `docker compose logs` 能看到的就是这个被轮转的窗口；
  healthcheck 与升级流程都不依赖它（升级时读的是 helper 容器的日志）。
