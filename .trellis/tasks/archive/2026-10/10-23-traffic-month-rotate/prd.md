# 按月重置流量在服务端不生效 —— 排查与修复方案

## Goal

用户报告：节点开了「按月重置流量」，但服务端累计流量只增不减，面板百分比从 ~49% 一路涨。
本次交付：**只读排查**清楚各项机制与断点，给出 P0 两方案取舍与后续实施计划；**本轮不改代码**。

## 用户裁决（本轮范围）

- 「流量虚高」一项（服务端累计 ≈539 GB 与 agent 同窗口 ≈253.6 GB 的 2.12 倍差异）**用户判定测量有误，移出范围**，不再投入。
- 其余各项（P0 归零不生效、时区/边界口径、面板展示口径、metricstore 两级分辨率不一致）**要查清"怎么回事"**。

## 事实基线（用户提供，勿重复调查）

1. `client_traffic_totals` 单行：`up_total` ≈262.19 GB、`down_total` ≈276.73 GB（合计 ≈539 GB），`updated_at` 持续更新；
2. 该节点 `traffic_limit` = 1 TiB、`traffic_limit_type = 'sum'`；面板百分比 ≈49% = 539 GB ÷ 1 TiB；
3. agent 侧：`--month-rotate != 0` 时上报 `GetTotalTrafficBetween(GetLastResetDate(monthRotate), now)`（**本周期值**，重置日 00:00 掉回 ~0）；
4. server 侧：`AccumulateTraffic` 按**单调开机计数器**处理（注释："跨重启只增不减"），把周期回滚当成"计数器归零"⇒ 增量为 0，累计不动；
5. 二进制中与本表相关的符号只有 `InitTrafficTotals` / `AccumulateTraffic` / `GetAllTrafficTotals` / `GetTrafficTotal` / `DeleteTrafficTotal` + metricstore 的 `trafficAccumulation` / `reportTrafficState` / `reportTrafficValues`——**无任何 Reset/Zero/Rollover**；
6. `configs` 34 键无 month/reset/traffic 项；`tasks` 0 行；`clients` 表**无** `month_rotate` 列；前端已出现 `admin.nodeTable.monthRotate` 类键（方向想做节点级配置，后端缺落地）；
7. 主机与容器均 UTC；`GetLastResetDate` 用 agent 本机时区 ⇒ 边界实为 UTC+8 的 22 号 08:00；`resetDay` 越界（<1 或 >31）时返回 `currentDate` ⇒ 区间恒空 ⇒ 流量恒 0；
8. metricstore 同日 rollup 求和：`resolution=60s` = 5.74 GB vs `resolution=300s` = 13.45 GB（agent 实测 13.96 GB），差 2.3 倍；
9. `migration_legacy_monitoring_to_metric_store_done = false`（旁证，仅用于判断旧路径是否仍在写）。

## 要求（本轮只读产出，不实施）

**P0 · 让"按月重置"真正生效**：给出两方案的可落地设计与取舍——
- 方案 1：服务端检测"周期回滚"（上报值显著下降且已跨越该节点重置日）⇒ 归零/重算基线；
  必须与"计数器归零不产生负增量"并存，能区分 (a) 进程/机器重启归零、(b) 周期回滚、(c) 抖动；
  覆盖换机 / UUID 复用 / 长时间离线后上线。
- 方案 2：重置日搬到服务端（节点级配置），服务端自算周期边界，agent 只报开机计数器。
- 取舍维度：改动面、老 agent 兼容、存量数据与配置迁移、可验证性、语义清晰度。

**P1 · 时区口径显式化**：明确周期边界时区（建议显式配置 + UI 标注边界时刻）；`resetDay` 越界值给出明确行为（拒绝保存或显式提示），不得静默退化成"恒 0"。

**P2 · 面板口径**：明确展示"本周期值"还是"累计值"（或两者并标注），避免"数字永不下降"的困惑。

**P2 · metricstore 一致性**：解释 60s / 300s 两级 rollup 求和差异的代码级原因，给出 gauge 聚合语义定义与修正方向。
