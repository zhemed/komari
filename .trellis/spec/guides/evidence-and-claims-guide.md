# Evidence & Claims Guide（结论的证据标准）

> 起因：2026-09-17 我们把一个**未经验证的因果结论**当成"已定位的原因"写进了公开的发布说明、
> 维护文档、代码注释、归档 PRD 和 journal，并据此提出过修复方案。用户判定为严重错误。
> 本指南是为这一类错误写下的机械规则，**不是"要更严谨"这类口号**。

---

## 两类可以写进文档的句子

| 类型 | 允许的写法 | 例子 |
|---|---|---|
| **观测**（可直接复现的测量） | 写数字 + 测量方法 + 命令/查询 | "636 个分钟逐分钟零误差（本桶 Σ增量 vs 相邻桶 `last_val` 差值，脚本见 §5）" |
| **推断**（解释观测的机制） | 必须带置信度与**判别性实验** | "最可能的原因是 X；判别方法是 Y（做 Y 会看到 Z），实测结果：…" |

**禁止**：把推断写成观测。具体禁用措辞（除非已有判别性证据）：**确因、已定位、根因是、
实测表现为、必然导致**。

---

## 写下结论前的三个机械检查

1. **测量方法自证**：同一个事实用**两种独立方法**核对过吗？
   - 反例（真实事故）：我们用 `bucket_milli` 过滤 60s 桶的同时，又拿 300s 桶的差值做对照，
     两种分辨率混在一个比较里，得出"05:38 只记到 5.5 KB 而计数器涨 190 KB"的假象。
     正确做法：先证明"同一方法在两个相邻窗口上自洽"（本例中端点对齐后逐分钟零误差），再下结论。
2. **判别性实验**：列出的竞争假设里，有没有一个观测是"只有 H1 为真才出现"？
   - 反例：把"增量偏低"归因到"v1/v2 双通道交错上报"，但从没验证过节点是否真的在两条通道间切换过
     （agent 日志里只有 v2 WebSocket）。**代码路径存在 ≠ 实测触发过。**
   - 正例（本次修复）：直接对拍"面板同款请求的点值"与"库中真实分钟量"，一个命令区分
     "数据丢失"与"查询聚合错误"两个假设。
3. **置信度声明**：证据只支持到哪一步，就写到哪一步。
   - 写"这个缺陷存在且逻辑必然触发，但**没有证据**表明它在生产触发过"是可以的；
     写"这就是原因"是不可以的。

## 结论被推翻时：全落点更正（不许只改一处）

一条错误结论通常散落在多个地方。更正时必须**全量搜出来**，每处都加**带日期的更正说明**，
不重写历史（归档 PRD / journal / 已发布的 release notes 都是记录，改动要留痕）：

```bash
# 用错误结论里的特征词全仓搜，逐个确认
grep -rn "双通道\|扎堆\|确因\|实测表现为" --include="*.md" --include="*.go" . | grep -v node_modules
```

落点清单（本次实际涉及的，按此对照）：
- 用户可见文档：`README.md`、`docs/MAINTAINING.md`、**已发布的 GitHub release notes**（用 `gh release edit`）
- 代码：注释、测试注释、常量命名
- 过程记录：`.trellis/tasks/**/prd.md`、`.trellis/workspace/**/journal-*.md`（含索引里的标题行）
- 规范：`.trellis/spec/**`

---

## 发布前的强制检查（与 `docs/MAINTAINING.md` §3.4 配合）

发布说明里每出现一条"修复/原因/已知问题"，都要能回答：

- [ ] 这条结论对应哪个**命令或测试**？把它写进发布说明。
- [ ] 它是观测还是推断？推断是否标了置信度？
- [ ] 如果是"已知问题"，是否写清了**下一步实验**，而不是写一个像原因的东西？
