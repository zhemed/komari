## 2. 为什么"最严重"：四条同时成立

1. **破坏了产品核心承诺。** 这条仓库线对用户最要紧的一句话是"**已发布 = 正在跑**"。compose 线里的
   失败模式会**静默**打破它：面板升级"成功"，但文件 tag 落后，下一次容器重建/`up -d` 就把二进制
   拉回旧版本——用户以为在跑 0.0.18，实际跑 0.0.17。
2. **失败是静默的。** 没有报错、没有日志、面板照常显示升级成功。破坏核心承诺**又不告诉你**，
   比直接报错严重一个量级：它不会自愈，也不会自报，只会在某次重启或改文件时暴露。
3. **它已经公开了。** 0.0.18 的 release notes 把这条写成"按我们文档用 host 网络部署的实例，
   装了这个版本才真正启用重建容器升级"——**发布说明对着用户承诺的正是这条带缺陷的能力**。
   已发布的历史不能改，撤下不可逆。
4. **回退不干净。** 为了撤销它，必须整条弧线回滚 + 生产二进制降级 + 留一堆待清理物
   （线上 release、镜像、`/opt/docker/komari` 的三份数据副本）。回退成本本身就是严重性的度量。

## 3. 机制：到底怎么坏的（观测/推断分开）

**观测（可复核）**

- O1 生产容器创建于 0.0.17 时期，早于"tag 自动同步"功能；容器 label
  `com.docker.compose.project.config_files` 在创建时写入，此后不随文件改名而更新。
- O2 实测：改名/新增同名文件后，`docker compose up -d` 不重建容器（配置未变），label 保持旧值；
  必须 `--force-recreate` 才刷新（本次弧线中"已实测"记录在归档任务的 research 里）。
- O3 `dd0486a` 的检测逻辑是"从自身容器 label 读 compose 文件路径"，读不到时**完全跳过、不留副作用**。
- O4 实测（`dd0486a` 提交信息）：host 网络下原两条自识别线索（hostname / cgroup）全失效 →
  静默退回容器内替换，B 策略形同虚设；修法是加第三条线索（`/proc/self/mountinfo` bind 挂载比对）。

**推断（标置信度）**

- I1（高）生产正是"label 指旧文件名"的现场：容器在 rename 之前创建。即便不依赖 I1，
  O1+O2+O3 已经足够说明**rename 与 label 之间存在真实的失效组合**，且失效是静默的。
- I2（高）即使 0.0.18 的 host 网络修复生效，"auto-sync 找不到文件路径"这条缺失链条仍只导致
  静默跳过——补了一处失败，没有补这道失败。

## 4. 根因（五层，从表面到系统）

| 层 | 断点 | 具体表现 |
|---|---|---|
| L1 表面（集成） | 功能与生产形态不匹配 | 0.0.18 **发布前从未在生产的 compose 项目上跑过一次真实升级**；测试只在自建的临时 compose 上做过 |
| L2 设计 | 把**引擎运行时元数据**当稳定依赖 | tag 同步的触发条件（容器 label 里的 compose 文件路径）由 docker 写入、随文件改名失效，而文件改名是我的脚本自己做的动作 |
| L3 契约 | 静默降级 | 取不到 label 就跳过、自识别失败就退回容器内替换，两处都**无声**；调用方看到的是"升级成功" |
| L4 方法 | "我有测试" ≠ "我验过这条路" | 单测/临时 compose E2E 全绿；同一轮里还有个更刺眼的例子——回归测试用 `sleep 1` 规避了同秒碰撞路径，于是测试**恰好绕过了**真实存在的 bug 路径（后来才补上微秒级唯一化） |
| L5 系统 | 发布纪律被自己的流程奖励 | 用户自己的规矩"已发布 = 正在跑"意味着**发布本身就是最后一道验证**；这次把一个未在生产环境验证过的自动机制发出去，等于把验证成本转嫁给生产与用户 |

## 5. 防复发（硬规则 + 机械闸门）

### 5.1 硬规则（写代码前先读这一节）

1. **版本同步只能吃自己写的文件。** upgrade 路径不得依赖容器 label、`config-hash`、compose 文件名
   优先级、镜像 tag 之类"引擎运行时元数据"来决定**版本一致性**。要做，就落一个配置文件
   （例如 `.komari/deployed-version`）由升级流程自己写——同仓库、同权限、可离线断言、可审计。
2. **会破坏"已发布 = 正在跑"的分支，禁止静默降级。** 要么显式失败，要么把"实际用的模式"打出来
   （日志 + 面板可见），让不一致**立刻可见**。判据：任何"读不到就跳过"的分支，如果跳过会导致版本
   与文件不一致，就必须留下可见痕迹。
3. **改生产形态的每一步，必须在隔离实例走完一遍完整升级**（含失败路径、含改名/迁移这种元数据变更），
   才允许在生产执行。生产不是第一次跑的地方。
4. **一个测试只证明它实际走过的那条路。** 测试里的 `sleep`、绕过、mock 掉的路径，都等于把那条路
   划到覆盖之外；要么覆盖它，要么在规范里写明"这条路径未验证"。
5. **发布说明不许把未在生产验证的机制写成"已启用/已生效"。** 措辞按证据指南走（观测 vs 推断）。

### 5.2 机械闸门（`scripts/check-repo.sh` 第 13 项，2026-09-19 加）

第 13 项扫描 `internal/upgrade/` 与 `cmd/dockerSelfRecreate.go`（**只扫代码，不扫注释与文档**），
一旦出现 `com.docker.compose`、`DetectSelfContainerID`、`selfid.go`、`compose.go` 这些
"引擎运行时元数据依赖"的符号就报红，并提示必须先读本节与 §5.1 第 1、2 条。

- 判别性验证：对**已回滚的历史提交** `dd0486a` 跑同一规则，必须报红（当时确有这些符号）——
  证明规则不是"永远为绿"的摆设。
- 与 §5.1 第 1 条的分工：第 1 条讲"该怎么做"，第 13 项只保证"重新引入这类依赖时会被人看到"，
  它不评价实现好坏——别把它当成质量门禁。

## 6. 本次事故的可复用教训（超出 compose）

1. **"能跑通"与"用户会看到一致"是两件事**：升级的一致性属于**跨系统不变量**（面板↔文件↔容器↔镜像），
   单点测试证明不了它。
2. **改名的代价常被低估**：文件名的变更会同时改变**引擎写入的元数据**、用户脚本、历史文档与运维口令。
   本次 rename 只花了几行改动，代价是整条弧线回滚。
3. **回滚指令要当成需求**：本次事故的收尾阶段，我连续 4 次按猜测回滚错目标（README/基础镜像/compose 文件名/
   整体 compose），直到改为"先全面清点、再整弧回滚"才对。教训：**用户说"回滚"时，先问/先清点边界，
   不要用最像的那个当答案**。
4. **文档不是证据**：出问题的机制在文档里写得挺完整（连"未挂 socket 也能升级"都写了），
   但文档没有一处记录"生产上这条自动同步从未真正生效过"——因为**没人做过那次观测**。
